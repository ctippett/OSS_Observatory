# CyberBrief Production Workflow

**Status:** Sole authoritative production instruction set for the daily CyberBrief.
**Control plane:** `OSS_Observatory/` (this file, Schema v1, the executable schema, the validator, supporting automation).
**Data / archive plane:** `CyberBrief/Briefs/` and `CyberBrief/Data/` (TXT, JSON, CSV, `MORNING_BRIEF.md`, the Long Half-Life tracker, and all historical production artifacts). This file does not own that data and does not relocate it.

This document supersedes the dated prompt files under `CyberBrief/Prompts/` (most recently `April_11_2026_CyberPrompt.txt`) as the operating instructions for CyberBrief production. It preserves the mature research methodology those prompts established. What it changes is how the canonical JSON record is produced: **the JSON is no longer generated by serializing the TXT brief.** It is built independently from the same underlying research, against the Canonical Schema v1 contract, and validated before anything downstream depends on it.

Read this file in full before running a CyberBrief. Do not reconstruct instructions from memory of a prior run.

## 1. Pipeline overview

A CyberBrief run is eight stages, in order:

1. **Research** — gather today's cybersecurity signal per the methodology in Section 2.
2. **Build the analytical brief** — select, classify, and synthesize items per Section 2's rules. This internal synthesis is the shared source for both outputs below; neither output is derived from the other.
3. **Write the human-readable TXT brief** — Section 3.
4. **Build the canonical JSON record independently, per Schema v1** — Section 4. Built from the same research and synthesis as the TXT brief, not by transforming or parsing the TXT.
5. **Validate the candidate JSON** against `cyberbrief.schema.json` using the validator — Section 5. This gate runs before step 7.
6. **Produce the CSV signal roll-up** — Section 6.
7. **Update persistent trackers/state** (`MORNING_BRIEF.md`, the Long Half-Life tracker) — Section 7. Only reached on a successful validation.
8. **Present the finished brief** — Section 8.

The critical architectural point: **steps 3 and 4 are siblings, not a pipeline.** Both are produced from the analytical brief built in step 2. The TXT is not parsed to build the JSON, and the JSON is not summarized to build the TXT. This is what eliminates the schema drift that comes from treating one artifact as a rendering of the other.

Every run also produces a **run record** — a small, human-readable audit artifact tracking when the run happened, which stages completed, and why any stage failed or was skipped. It is created before stage 1 begins and updated as each stage above completes, fails, or is skipped. It is not part of the CyberBrief methodology or the Schema v1 contract, is not gated by validation, and is preserved even for a failed or partial run. See Section 12.

## 2. Research and analytical methodology (behavioral baseline — preserved)

This section preserves the mature CyberBrief methodology. It is substantively unchanged from `April_11_2026_CyberPrompt.txt`; only the downstream output mechanics (Sections 3-8 below) have changed.

### 2.1 Strategic purpose
Gather daily intelligence on concrete cybersecurity events, actions, and decisions. Produce a same-day internal intelligence brief for AppSec stakeholders, and preserve a high-integrity daily research log to support longitudinal analysis and future synthesis. Daily execution emphasizes factual logging; interpretation accumulates over time.

### 2.2 Longitudinal research arcs (interpretive overlays)
Track strategic arcs that transcend daily news flow. Arcs inform classification but are not daily output requirements — reference them when relevant, do not force arc mapping.

- **2.1 OSS Trust, Value, Independence & Generative Leverage** — how agentic AI systems are changing the trust model for OSS, tracking both generative leverage (innovation, AI acceleration, capability compounding) and contestation (capture, manipulation, governance distortion). First-Order OSS Model Shift Rule: when a named OSS project, foundation, or sponsor changes how responsibility, incentives, funding, or assurance are structured, treat this as a Structural Shift signal even if no exploit occurred. Capture occurs when external actors alter OSS governance or autonomy via funding leverage, infrastructure dependency, regulation, covert influence, or supply-chain manipulation.
- **2.2 SBOM & Software Supply-Chain Transparency** — evolution from static SBOMs toward dynamic provenance, attestation, dependency intelligence, and enforcement.
- **2.3 AI Policy, Governance & Ethical Integrity** — alignment, accountability, safety norms, and compute geopolitics.
- **2.4 CyberCrime & Adversary Economics** — adversary incentives, economics, tooling, and ecosystem dynamics.

### 2.3 Daily focus areas
CyberCrime; AppSec (OSS priority); AI Policy (including quantum when tied to AI or compute); Hacktivism; Ethical Hackers; Regulatory/Policy. AI impact is assessed across all areas.

### 2.4 Analytic signal types and half-life
Classify each item as exactly one:

- **Incident Signal (Short Half-Life)** — tactical events; value decays after remediation.
- **Policy Evolution Signal (Medium Half-Life)** — institutional or regulatory movements; measured in quarters.
- **Structural Shift Signal (Long Half-Life)** — named actions or decisions that change assumptions, incentives, governance, or capability baselines; measured in years. Gate: must describe a specific, observable action or decision by a named organization, project, or governing body. Positive Structural Signals (credible actions that materially improve OSS or AI sustainability, governance, or assurance) qualify even without an incident trigger.

### 2.5 Inflection Watch (conditional marker)
Apply only when significance depends on recurrence or scaling. Not itself a claim of importance.

### 2.6 Micro-tracking directives
Apply only when events occur:
- **Registry Abuse** — npm, PyPI, OpenVSX, VS Code Marketplace.
- **LLM Misuse** — jailbreaks, poisoning, unsafe tool use, or agentic misuse.

### 2.7 Selection criteria
- **Item count:** up to 6 significant developments first reported in the last 24 hours. Fewer is acceptable.
- **Deduplication:** do not repeat an item unless a material update occurred. This includes checking for gaps against the prior run and handling retrospectives (multi-day catch-up briefs, named `<start>_<end>_cyberbrief_retrospective`) when a run was missed — a retrospective covers the full missed date range rather than silently dropping it.
- **Coverage:** aim to cover all focus areas over time; if none occurred today for an area, state that explicitly rather than forcing inclusion.
- **Breach handling:** include at least one newly disclosed breach when present, naming affected organizations explicitly.
- **Referent requirement:** each item must name at least one concrete referent (organization, project, foundation, government body, or adversary group); exclude items without one.
- **Industry research inclusion:** include major industry or vendor research only on its initial publication day, as a single item.

### 2.8 Adversary Spotlight (conditional)
Include only when a named threat actor materially matters today: who they are, primary tactics, recent activity or impact.

### 2.9 Per-item research fields
For every selected item, establish: title, date, source, domain, surface, signal type, half-life, AI impact (None / Enabling / Amplifying / Governing / Targeted), summary, extracted statistics, and — when applicable — breach-specific research detail (e.g. records exposed, data types, discovery vs. disclosure, attack vector, regulatory clock — useful for the TXT brief's prose and for `extracted_statistics`). This research-level vocabulary is not a JSON field-naming instruction: when building the JSON, breach information goes into the five-field `breach_specifics` object defined in Section 4.5, whose field names control.

Also assess, per item, the lightweight **IAD-Signal marker**: how strongly the item warrants later institutional analysis through the Institutional Analysis and Development lens, and which IAD dimensions (Actors, Rules-in-Use, Arena, Incentives, Interactions, Outcomes, Levers) appear potentially relevant. This is a relevance-plus-dimensions marker, not a written IAD analysis — see Section 4.4 for exactly how this becomes the JSON-only `iad_signal` field. It is a per-item judgment, independent of whatever day-level "IAD LENS" framing (if any) goes into the TXT brief under Section 3.

### 2.10 Daily Narrative (required)
Operational synthesis answering: what changed today; did anything escalate, stabilize, or break precedent; and the aggregate role of AI today, in one sentence. No speculation, no restating background conditions.

### 2.11 Strategic Insights
One emerging trend, one policy or market implication, one blind spot or quiet area.

### 2.12 Industry Research Reference (persistent baseline)
A cumulative list of key industry or vendor research used as structural baselines. Append only when a genuinely new report is released; once added, entries persist across briefs. Do not summarize or analyze here — see Section 3.3 for where this lives (TXT-only).

### 2.13 Source universe (coverage baseline, not an allowlist)
Research should cover the established CyberBrief source universe below as a coverage baseline. This is not an allowlist: the LLM remains free to discover and use additional credible sources relevant to today's signals, beyond this universe.

- **Government:** CISA, FBI, DOJ, EUROPOL, ENISA, NCSC, CERT-EU, JPCERT/CC, ACSC (Australia)
- **Policy & Research:** RAND, Brookings, MITRE, Atlantic Council, Carnegie Endowment (Cyber Policy Initiative), CFR, Lawfare, UK AI Security Institute (AISI), The Alan Turing Institute
- **Journalism & Tech Industry:** KrebsOnSecurity, BleepingComputer, Ars Technica, CyberScoop, Wired, The Record, Bloomberg Tech, Microsoft, Meta, Amazon, Google, Bloomberg, NYT, Hacker News, Dark Reading, TechCrunch Security
- **Vendor & Security Research:** Mandiant/Google Cloud Threat Intelligence, CrowdStrike Blog, Cisco Talos/TalosIntelligence, Palo Alto Unit 42, Wiz, Checkmarx, Sysdig, Recorded Future, Rapid7, SentinelLabs, Cyble, Black Duck, Synopsys, Microsoft Threat Intelligence (MSTIC), ESET Research, Check Point Research
- **Ethical Hacker & Bug Bounty:** HackerOne Hacktivity, Bugcrowd Blog
- **OSINT/Social:** Reddit, X, LinkedIn, Telegram, Dark Web forums, Mastodon/Fediverse security communities, GitHub repositories
- **Primary Breach Disclosures:** SEC EDGAR Form 8-K Item 1.05, HHS OCR Breach Portal, State AG notification sites, UK ICO, OAIC (Australia), CNIL (France)
- **Secondary Breach Tracking:** DataBreaches.net, Have I Been Pwned (HIBP) blog/announcements

### 2.14 Evidence quality
Use evidence appropriate to the claim. Prefer primary and authoritative sources when available. Use credible secondary reporting for discovery and context. Corroborate material claims when the underlying evidence is uncertain, disputed, indirect, or based primarily on secondary reporting. This is a governing principle, not a mechanical two-source requirement.

### 2.15 Collection versus selection
Source discovery and research (Sections 2.13-2.14) produces candidate developments, not final signals. The existing selection criteria in Section 2.7 — unchanged, including the up-to-6-items guidance ("fewer is acceptable") — determine which candidates become final CyberBrief items.

### 2.16 Evidence preservation (source URLs)
For every selected CyberBrief item, preserve the HTTP/HTTPS URL(s) of the evidence actually used to support that observation — not every page encountered during research, only evidence materially used to support the selected observation. These URLs become the item's required `source_urls` array in the canonical JSON record (Section 4.3). `source` remains the separate human-readable source/outlet field; `source_urls` holds one or more supporting evidence URLs.

## 3. Writing the TXT brief (human-readable artifact)

Write the canonical daily TXT brief using the synthesis from Section 2. This is the artifact for human review.

### 3.1 Format
Format is canonical — do not change section structure or ordering without an explicit decision from Charles. The current section order (per recent production briefs) is: daily intelligence summary header; per-item entries (each with Summary and Extracted Statistics, and other Section 2.9 fields as written); Adversary Spotlight (when present); Registry Abuse Watch / LLM Misuse Tracker (when present); Inflection Watch; Longitudinal Arcs; Daily Narrative; end-of-brief marker.

### 3.2 IAD LENS (TXT-only)
The TXT brief may carry a day-level **"IAD LENS"** line or section — an analytical throughline for the day, in prose. This is a TXT presentation element only.

### 3.3 Industry Research Reference (TXT-only)
The TXT brief may carry an **"INDUSTRY RESEARCH REFERENCE (Cumulative Baseline)"** section per Section 2.12. This is a TXT presentation element only.

### 3.4 Boundary rule
**Neither of the two sections above may cause a corresponding top-level field in the canonical JSON.** `iad_lens` and `industry_research_reference` are not valid top-level JSON keys under Schema v1 (`cyberbrief.schema.json` sets `additionalProperties: false` at the top level, and neither key is declared) — see Section 4.8. Writing the TXT does not drive, and is not driven by, building the JSON.

### 3.5 Output
Write to `CyberBrief/Briefs/YYYYMMDD_cyberbrief.txt` (or `CyberBrief/Briefs/<start>_<end>_cyberbrief_retrospective.txt` for a retrospective covering a missed range), using the current date(s) for the run.

## 4. Building the canonical JSON record (independent, Schema v1)

### 4.1 The JSON is a research record, not a rendering
The canonical JSON is an independently constructed structured record of the day's research, governed by `cyberbrief.schema.json` and described in full in `Canonical_CyberBrief_Schema_v1.md`. Build it from the same analytical brief (Section 2) used for the TXT — do not derive it by parsing, transcribing, or "serializing" the TXT file, and do not treat TXT section headings as a source of JSON key names. This replaces the prior `Feb_20_2026_JSON_Serialization_Prompt.txt` approach, which instructed literal serialization of TXT sections into JSON and is the documented cause of schema drift (see Section 4.8).

### 4.2 Required top-level shape
Per `cyberbrief.schema.json`:

- Required: `date`, `signal_counts` (`structural_shift`, `policy_evolution`, `incident` — integer counts), `items` (array).
- Optional, include when applicable, `null` when not: `micro_tracking`, `inflection_watch`, `longitudinal_arcs`, `daily_narrative`, `adversary_spotlight`, `strategic_insights`.
- `adversary_spotlight`'s and `micro_tracking`'s required internal shapes, when either is present, are fixed and fully required — see Section 4.6 and Section 4.7 respectively.
- No other top-level keys are permitted (`additionalProperties: false`).

### 4.3 Required item shape
Each entry in `items` requires: `title`, `date`, `source`, `source_urls` (array of one or more HTTP/HTTPS evidence URLs — see Section 2.16 for what to preserve; `source` stays the human-readable source/outlet field, `source_urls` is separate and required), `domain`, `surface`, `signal_type` (`Incident` | `Policy Evolution` | `Structural Shift`), `half_life` (`Short` | `Medium` | `Long`), `ai_impact` (`None` | `Enabling` | `Amplifying` | `Governing` | `Targeted`), `arc`, `iad_signal`, `summary`, `extracted_statistics` (array, may be empty), `breach_specifics` (object or `null` — required internal shape specified in Section 4.5). No other item keys are permitted.

### 4.4 `iad_signal` (item-level, JSON-only)
For every item, set:

```json
"iad_signal": {
  "relevance": "None | Low | Medium | High",
  "dimensions": ["Actors", "Rules-in-Use", "Arena", "Incentives", "Interactions", "Outcomes", "Levers"]
}
```

`dimensions` is zero or more of the seven allowed values; when `relevance` is `"None"`, `dimensions` must be `[]`. This is the JSON-only formalization of the Section 2.9 IAD-Signal marker — assess it from the item itself, per the marker definition in `Canonical_CyberBrief_Schema_v1.md` §4.10. Do not derive it from, or make it depend on, the TXT's day-level "IAD LENS" line (Section 3.2) — they are different things at different levels (item vs. day) serving different purposes (structured marker vs. narrative prose).

### 4.5 `breach_specifics` (item-level, object or `null`)

Required on every item; its value is `null` unless the item involves a data breach or related compromise, in which case it is an object containing **exactly these five fields — no others**:

```json
"breach_specifics": {
  "victim": "...",
  "actor": "...",
  "vector": "...",
  "data": "...",
  "status": "..."
}
```

- `victim` — string. The affected organization(s) or population.
- `actor` — string. The attributed actor, when known.
- `vector` — string. The compromise vector.
- `data` — string. The exposed or affected data.
- `status` — string. Current breach/disclosure status.

These five names are the only field names Schema v1 recognizes for `breach_specifics` (`cyberbrief.schema.json`'s `breachSpecifics` definition sets `additionalProperties: false` and requires all five). **The executable schema's field names control.** Section 2.9's research-level breach vocabulary (records exposed, data types, discovery vs. disclosure, attack vector, regulatory clock) describes what to investigate and is useful for the TXT brief's prose — it is not a JSON key-naming instruction. When building the JSON, map that research into exactly the five fields above.

For items without applicable breach-specific information: `"breach_specifics": null`.

### 4.6 `adversary_spotlight` (top-level, object or `null`)

Included only when Section 2.8's condition is met (a named threat actor materially matters today); `null` or omitted otherwise.

When present, `adversary_spotlight` is an object containing **exactly these eight fields — no others — all required**:

```json
"adversary_spotlight": {
  "actor": "...",
  "classification": "...",
  "known_aliases": ["...", "..."],
  "attributed_nation": "...",
  "active_since": "...",
  "todays_relevance": "...",
  "ttps_today": "...",
  "historical_pattern": "..."
}
```

- `actor` — string. Who the actor is.
- `classification` — string (e.g. Nation-State, Cybercriminal, Hacktivist).
- `known_aliases` — **array of strings.** Not a single string — this has already drifted in production practice (see below).
- `attributed_nation` — string.
- `active_since` — string.
- `todays_relevance` — string. Why this actor matters today (Section 2.8's "recent activity or impact").
- `ttps_today` — string. Primary tactics relevant today (Section 2.8's "primary tactics").
- `historical_pattern` — string.

Schema v1 (`cyberbrief.schema.json`'s `adversarySpotlight` definition) sets `additionalProperties: false` and requires all eight fields whenever the object is present. Section 2.8's three-line description ("who they are / primary tactics / recent activity or impact") is the research-level summary of what to establish; it maps onto `actor` / `ttps_today` / `todays_relevance`, but the four additional structural fields above (`classification`, `known_aliases`, `attributed_nation`, `active_since`) must also be populated — they are not optional extras. In particular, `known_aliases` must be a JSON array even when there is only one alias or the aliases read naturally as a short descriptive phrase; do not write it as a single free-text string (a real production file has done this, and it fails validation).

### 4.7 `micro_tracking` (top-level, object or `null`)

When `micro_tracking` is included (per Section 2.6), it must contain **both** of the following string fields — never just one:

```json
"micro_tracking": {
  "registry_abuse": "...",
  "llm_misuse": "..."
}
```

Section 2.6 applies Registry Abuse and LLM Misuse tracking independently ("apply only when events occur"), but Schema v1 (`cyberbrief.schema.json`'s `microTracking` definition) requires both keys whenever the object itself is present — there is no partial `micro_tracking` object. If one area had no meaningful development today, say so explicitly and briefly (e.g. `"registry_abuse": "No registry abuse activity observed today."`) rather than omitting that key. If neither area had any activity, omit `micro_tracking` entirely (set it to `null`) rather than including an object of two "nothing happened" strings.

### 4.8 Explicit prohibitions
- Do **not** generate a top-level `iad_lens` field. (Production JSON has historically carried a stray top-level `iad_lens` string mirroring the TXT's day-level IAD LENS sentence — this violates Schema v1 and is exactly the drift this workflow exists to stop. Confirmed by running the fixed validator against `CyberBrief/Data/20260825_cyberbrief.json`: `Additional properties are not allowed ('iad_lens' was unexpected)`.)
- Do **not** generate a top-level `industry_research_reference` field.
- Do not infer or add a JSON field merely because a similarly named section or heading exists in the TXT brief.
- Do not modify Schema v1 to make the day's output easier to fit. If a real day's research doesn't fit the schema, that's a validation failure to report (Section 5), not a reason to loosen the contract.

### 4.9 Candidate file — do not overwrite the canonical record until validated
Write the JSON to a **candidate** path first, not directly to the day's canonical filename:

```
CyberBrief/Data/.candidate/YYYYMMDD_cyberbrief.candidate.json
```

(create the `.candidate/` subdirectory if it does not exist). Only after the candidate passes validation (Section 5) is it copied/renamed to the canonical path `CyberBrief/Data/YYYYMMDD_cyberbrief.json`. This guarantees an invalid candidate can never overwrite an already-valid canonical record for that date, and gives a concrete artifact to inspect when validation fails.

## 5. Validation gate

Run, from any working directory:

```
python3 OSS_Observatory/validators/cyberbrief_validator.py CyberBrief/Data/.candidate/YYYYMMDD_cyberbrief.candidate.json
```

(use the actual absolute or relative path to the candidate file for that run; the validator resolves `cyberbrief.schema.json` relative to its own location, not the caller's cwd, so this works regardless of where the run's working directory happens to be).

### 5.1 On success
`CYBERBRIEF PASSED VALIDATION`. Promote the candidate: copy/rename it to `CyberBrief/Data/YYYYMMDD_cyberbrief.json`. Proceed to Section 6.

Update the run record (Section 12.4): mark stage 4 (Schema validation) `PASS`, and mark stage 5 (Canonical JSON promotion) `DONE` with the promoted canonical path.

### 5.2 On failure
The validator exits non-zero and prints `CYBERBRIEF FAILED VALIDATION`, the exact `Reason:`, and the `Location:` (JSON path) of the offending field. When this happens:

- **Report the exact validation error to Charles** — the reason and location, verbatim from the validator output.
- **Do not treat the run as successful.**
- **Do not update `MORNING_BRIEF.md`.**
- **Do not update the Long Half-Life tracker.**
- **Do not present the invalid candidate as the canonical daily brief.**
- **Do not silently weaken or modify the schema to make the output pass.**
- Leave the invalid file at its candidate path (do not delete it — it's the evidence) and do not touch the existing canonical JSON for that date, if one already exists.
- The TXT brief (Section 3) may still be presented on its own merits — TXT output is not gated by JSON validation — but the run as a whole is not complete until the JSON is valid, and that should be stated plainly rather than left implicit.
- Update the run record (Section 12.4): mark stage 4 (Schema validation) `FAIL`, copying the validator's `Reason:` and `Location:` output into the run record verbatim, and mark stages 5-8 (Canonical JSON promotion, CSV roll-up, MORNING_BRIEF.md update, Long Half-Life tracker update) `SKIPPED (validation failed)`. The run record itself is still written — it is the evidence of the failure, not something withheld because the run failed.

## 6. CSV signal roll-up

Produce `CyberBrief/Data/YYYYMMDD_signal_rollup.csv`, one row per distinct signal pattern (not per story), grouped by Domain, Surface, and Signal Type — derived from the same validated set of items as the promoted JSON, not re-derived from TXT prose.

Columns, exact order: `Date, Domain, Surface, Signal Type, Distinct Signal Count, Volume, Comments`.

Volume classification: **Low** = 1 distinct story; **Medium** = 2-3; **High** = 4+.

Rules: do not invent or infer signals not present in the day's items; do not include story titles, summaries, or prose in this file — it is structured sensemaking, not narrative.

Produce the CSV only after the JSON has been promoted (Section 5.1) — if validation fails, do not produce a CSV for that run.

---

## 7. Update persistent trackers/state

Only after a successful validation and promotion (Section 5.1):

- Update `CyberBrief/Briefs/MORNING_BRIEF.md` with the day's brief summary and archive index entry.
- Update `CyberBrief/Data/LongHalfLife/LongHalfLife_Tracker_May2026.xlsx` with any new Structural Shift (Long Half-Life) items from today's run.

If the tracker file is locked (e.g. open in Excel — check for a `.~lock.*#` file alongside it before writing), do not force a write; note it in the run's presentation output and let Charles know it needs to be updated once the file is closed.

Update the run record (Section 12.3) for each of the two trackers independently: mark stage 7 (MORNING_BRIEF.md update) and stage 8 (Long Half-Life tracker update) each `DONE` or `SKIPPED (<reason>)`. A locked tracker is recorded on its own line, e.g. `SKIPPED (locked: .~lock.LongHalfLife_Tracker_May2026.xlsx#)` — this is the durable record of the skip, in addition to telling Charles in the run's presentation output.

## 8. Present the finished brief

Present the brief to Charles as today's CyberBrief. State plainly which of the three artifacts (TXT, JSON, CSV) were produced and, if the JSON failed validation, that the run is incomplete pending a fix — do not present a partial or invalid run as a normal, successful one.

Finalize the run record (Section 12.6): add the `Run completed` timestamp and confirm stage 9 (Brief presentation) is marked `DONE`, and that the other eight stage lines already reflect the run's actual outcome.

## 10. Scope boundary (what this workflow does not do)

- Does not touch or replace the existing scheduled CyberBrief task.
- Does not delete, move, archive, or modify historical CyberBrief JSON/TXT/CSV records, historical prompt files, or the older duplicate `Canonical_CyberBrief_Schema_v1.md` under `CyberBrief/Scripts/`.
- Does not commit or push anything in `OSS_Observatory/` to version control on its own initiative.
- Legacy cleanup (retiring the `CyberBrief/Scripts/` duplicate schema, retiring superseded `CyberBrief/Prompts/*` files, deciding what if anything moves) happens only after this workflow has produced and validated a real CyberBrief end-to-end, and only on explicit direction.

## 12. Run record (audit artifact)

Every CyberBrief run — whether it succeeds, fails, or is only partially completed — produces one run record. Its purpose is narrow: let a run's outcome be reconstructed from disk alone, six months later, without relying on chat or conversation history. It supplements the artifacts and gates already defined in Sections 3-8 and changes nothing about the CyberBrief methodology, Schema v1, the validator, or existing failure semantics.

### 12.1 Location and naming

- Daily run: `CyberBrief/Data/YYYYMMDD_run_record.md`
- Retrospective run: `CyberBrief/Data/<start>_<end>_run_record.md`

Same date-naming convention and same `CyberBrief/Data/` location as the canonical JSON and CSV (Section 9). Each run produces its own dated file; never overwrite or delete a prior date's run record.

### 12.2 Creation

Create the run record first, before Section 2 (Research) begins, with:

- `Run started` — current timestamp, ISO 8601 with timezone offset.
- `Run type` — `Daily` or `Retrospective (<start>–<end>)`.
- `Workflow ref` — `OSS_Observatory/cyberbrief_production_workflow.md`.
- `Workflow commit` — the current Git commit hash of the OSS_Observatory repository, captured via `git -C OSS_Observatory rev-parse HEAD` (or the equivalent invocation from the run's working directory). If the repository or command is unavailable, record `unknown` rather than blocking the run.
- The nine-stage checklist below (Section 12.3), all stages initially marked `PENDING`.

### 12.3 Stage checklist and updates

The run record tracks nine stages, each updated in place as it is reached:

1. Research / analytical brief (Section 2)
2. TXT generation (Section 3)
3. Candidate JSON generation (Section 4)
4. Schema validation (Section 5)
5. Canonical JSON promotion (Section 5.1)
6. CSV roll-up (Section 6)
7. MORNING_BRIEF.md update (Section 7)
8. Long Half-Life tracker update (Section 7)
9. Brief presentation (Section 8)

Each stage is updated to exactly one of `DONE`, `SKIPPED (<reason>)`, or — stage 4 only — `PASS`/`FAIL` (Section 12.4). Where a stage produces a canonical artifact, record its path on the same line, e.g.:

```
2. TXT generation                    DONE  -> CyberBrief/Briefs/YYYYMMDD_cyberbrief.txt
```

### 12.4 Recording validation

Stage 4 (Schema validation) is recorded as `PASS` or `FAIL`, per Section 5.

On `PASS`: stage 5 (Canonical JSON promotion) is marked `DONE` with the promoted canonical path, per Section 5.1, and the run proceeds normally through stages 6-9.

On `FAIL`: copy the validator's `Reason:` and `Location:` output into the run record verbatim beneath stage 4, then mark stages 5-8 (Canonical JSON promotion, CSV roll-up, MORNING_BRIEF.md update, Long Half-Life tracker update) `SKIPPED (validation failed)`, matching the existing prohibitions in Section 5.2. Stage 9 (Brief presentation) is still marked `DONE` once Section 8 reports the failed run to Charles — the run record does not change what gets presented, only confirms that the presentation happened.

### 12.5 Recording nonfatal exceptions

A stage skipped for a reason other than validation failure (for example, Section 7's locked-tracker case) is recorded on its own line with a one-line cause, not a separate log:

```
8. Long Half-Life tracker update     SKIPPED (locked: .~lock.LongHalfLife_Tracker_May2026.xlsx#)
```

### 12.6 Completion

At Section 8 (Present), add `Run completed` with a timestamp and confirm the final status of all nine stages reflects the run's actual outcome.

### 12.7 Preservation

The run record is written and updated regardless of validation outcome. Unlike the canonical JSON and CSV (Sections 4.9 and 6), it is not gated behind validation success — its purpose is specifically to preserve evidence of failed or partial runs. Do not fold it into, or derive it from, the canonical JSON, the TXT brief, or MORNING_BRIEF.md; it is a separate, minimal artifact.

### 12.8 Template

```
# CyberBrief Run Record — YYYY-MM-DD

Run started:      YYYY-MM-DDTHH:MM:SS±TZ
Run type:         Daily
Workflow ref:     OSS_Observatory/cyberbrief_production_workflow.md
Workflow commit:  <git commit hash | unknown>

## Stage status
1. Research / analytical brief       PENDING
2. TXT generation                    PENDING
3. Candidate JSON generation         PENDING
4. Schema validation                 PENDING
5. Canonical JSON promotion          PENDING
6. CSV roll-up                       PENDING
7. MORNING_BRIEF.md update           PENDING
8. Long Half-Life tracker update     PENDING
9. Brief presentation                PENDING

Run completed:     (not yet complete)
```

### 12.9 Scope

The run record is a single flat Markdown file per run — not a database, not a logging framework, not a telemetry system, and not a general audit subsystem. It does not track anything beyond the nine stages above. If future needs exceed what this file can hold, that is a deliberate design change to make explicitly, not a reason to let this section drift.
