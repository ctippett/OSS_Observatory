# CyberBrief Production Workflow

**Status:** Sole authoritative production instruction set for the daily CyberBrief.
**Control plane:** `OSS_Observatory/` (this file, Schema v1, the executable schema, the validator, supporting automation).
**Data / archive plane:** `CyberBrief/Briefs/` and `CyberBrief/Data/` (TXT, JSON, CSV, `MORNING_BRIEF.md`, the Long Half-Life tracker, and all historical production artifacts). This file does not own that data and does not relocate it.

This document supersedes the dated prompt files under `CyberBrief/Prompts/` (most recently `April_11_2026_CyberPrompt.txt`) as the operating instructions for CyberBrief production. It preserves the mature research methodology those prompts established. What it changes is how the canonical JSON record is produced: **the JSON is no longer generated by serializing the TXT brief.** It is built independently from the same underlying research, against the Canonical Schema v1 contract, and validated before anything downstream depends on it.

Read this file in full before running a CyberBrief. Do not reconstruct instructions from memory of a prior run.

## 1. Pipeline overview

A CyberBrief run is eight stages, in order:

1. **Research** — gather today's cybersecurity signal per the methodology in Section 2.
2. **Build the analytical brief** — select, classify, and synthesize items per Section 2's rules. This internal synthesis is the shared source for both outputs below; neither output is derived from the other.
3. **Write the human-readable TXT brief** — Section 3.
4. **Build the canonical JSON record independently, per Schema v1** — Section 4. Built from the same research and synthesis as the TXT brief, not by transforming or parsing the TXT.
5. **Validate the candidate JSON** against `cyberbrief.schema.json` using the validator — Section 5. This gate runs before step 7.
6. **Produce the CSV signal roll-up** — Section 6.
7. **Update persistent trackers/state** (`MORNING_BRIEF.md`, the Long Half-Life tracker) — Section 7. Only reached on a successful validation.
8. **Present the finished brief** — Section 8.

The critical architectural point: **steps 3 and 4 are siblings, not a pipeline.** Both are produced from the analytical brief built in step 2. The TXT is not parsed to build the JSON, and the JSON is not summarized to build the TXT. This is what eliminates the schema drift that comes from treating one artifact as a rendering of the other.

Every run also produces a **run record** — a small, human-readable audit artifact tracking when the run happened, which stages completed, and why any stage failed or was skipped. It is created before stage 1 begins and updated as each stage above completes, fails, or is skipped. When execution includes a material event a stage's final status alone would not accurately convey — a correction after validation or promotion, a repeated validation or promotion, or similar — that event is also logged in the run record's Execution Notes. It is not part of the CyberBrief methodology or the Schema v1 contract, is not gated by validation, and is preserved even for a failed or partial run. See Section 12.

## 2. Research and analytical methodology (behavioral baseline — preserved)

This section preserves the mature CyberBrief methodology. It is substantively unchanged from `April_11_2026_CyberPrompt.txt`; only the downstream output mechanics (Sections 3-8 below) have changed.

### 2.1 Strategic purpose
Gather daily intelligence on concrete cybersecurity events, actions, and decisions. Produce a same-day internal intelligence brief for AppSec stakeholders, and preserve a high-integrity daily research log to support longitudinal analysis and future synthesis. Daily execution emphasizes factual logging; interpretation accumulates over time.

### 2.2 Longitudinal research arcs (interpretive overlays)
Track strategic arcs that transcend daily news flow. Arcs inform classification but are not daily output requirements — reference them when relevant, do not force arc mapping.

- **2.1 OSS Trust, Value, Independence & Generative Leverage** — how agentic AI systems are changing the trust model for OSS, tracking both generative leverage (innovation, AI acceleration, capability compounding) and contestation (capture, manipulation, governance distortion). First-Order OSS Model Shift Rule: when a named OSS project, foundation, or sponsor changes how responsibility, incentives, funding, or assurance are structured, treat this as a Structural Shift signal even if no exploit occurred. Capture occurs when external actors alter OSS governance or autonomy via funding leverage, infrastructure dependency, regulation, covert influence, or supply-chain manipulation.
- **2.2 SBOM & Software Supply-Chain Transparency** — evolution from static SBOMs toward dynamic provenance, attestation, dependency intelligence, and enforcement.
- **2.3 AI Policy, Governance & Ethical Integrity** — alignment, accountability, safety norms, and compute geopolitics.
- **2.4 CyberCrime & Adversary Economics** — adversary incentives, economics, tooling, and ecosystem dynamics.

### 2.3 Daily focus areas
CyberCrime; AppSec (OSS priority); AI Policy (including quantum when tied to AI or compute); Hacktivism; Ethical Hackers; Regulatory/Policy. AI impact is assessed across all areas.

### 2.4 Analytic signal types and half-life
Classify each item as exactly one:

- **Incident Signal (Short Half-Life)** — tactical events; value decays after remediation.
- **Policy Evolution Signal (Medium Half-Life)** — institutional or regulatory movements; measured in quarters.
- **Structural Shift Signal (Long Half-Life)** — named actions or decisions that change assumptions, incentives, governance, or capability baselines; measured in years. Gate: must describe a specific, observable action or decision by a named organization, project, or governing body. Positive Structural Signals (credible actions that materially improve OSS or AI sustainability, governance, or assurance) qualify even without an incident trigger.

### 2.5 Inflection Watch (conditional marker)
Apply only when significance depends on recurrence or scaling. Not itself a claim of importance.

### 2.6 Micro-tracking directives
Apply only when events occur:
- **Registry Abuse** — npm, PyPI, OpenVSX, VS Code Marketplace.
- **LLM Misuse** — jailbreaks, poisoning, unsafe tool use, or agentic misuse.

### 2.7 Selection criteria

**Timezone:** all execution dates, daily periods, retrospective range boundaries, and Run Record dates use `America/Chicago` as CyberBrief's authoritative timezone — a named, DST-aware timezone (CST/CDT), never a fixed UTC offset; the correct offset varies by calendar date and must be resolved accordingly.

- **Item count:** target 6-8 developments per day — this range reflects what one practitioner can actually absorb in a single sitting: enough to stay current, not so much it becomes noise. This is a target, not a quota: fewer items, including zero, remains a valid, successful run whenever fewer genuinely informative developments exist (see Informativeness, below). Never pad the brief with a lower-quality or borderline story merely to reach the target. On a zero-item day, the TXT brief must state the zero-item result explicitly (Section 3.1), and the candidate JSON must remain schema-valid using the zero-item representation in Section 4.2.
- **Informativeness (the daily-selection standard):** select an item because it is real, sourced, timely — first reported or meaningfully advanced in the last 24 hours — and genuinely worth an AppSec practitioner knowing about today. This is the operative test for what goes in the daily brief. It is independent of an item's signal-type classification (Section 2.4) and independent of its eligibility for Long Half-Life tracker promotion (Section 7): those govern what gets tracked longitudinally, not what gets reported today. Incident, Policy Evolution, and Structural Shift retain their existing analytical meanings and are assigned on their own terms (Section 2.4), not as a gate on daily inclusion.
- **Deduplication:** do not repeat an item unless a material update occurred. Duplicate checking covers the immediately preceding canonical run plus any canonical artifact whose coverage period overlaps the current research window. An ongoing story may be included again only when there is a material new development.
- **Retrospective boundary:** check for gaps against the prior run; when a run was missed, produce a retrospective (multi-day catch-up brief, named `<start>_<end>_cyberbrief_retrospective`) covering the full missed date range rather than silently dropping any of it. A retrospective covers only missed completed run periods. The current execution period always receives its own normal daily brief. Retrospectives repair history; they do not consume today's observation.
- **Coverage:** aim to cover all focus areas over time; if none occurred today for an area, state that explicitly rather than forcing inclusion.
- **Breach handling:** include at least one newly disclosed breach when present, naming affected organizations explicitly.
- **Referent requirement:** not a universal condition for daily inclusion — an item may be selected without naming a concrete referent if it is otherwise real, sourced, timely, and informative (see Informativeness, above). This is unchanged where an existing downstream mechanism genuinely requires one: Structural Shift classification (Section 2.4) independently requires a specific, observable action or decision by a named organization, project, or governing body as part of its own definition, and that requirement continues to govern Structural Shift classification and Long Half-Life tracker eligibility (Section 7).
- **Industry research inclusion:** include major industry or vendor research only on its initial publication day, as a single item.

### 2.8 Adversary Spotlight (conditional)
Include only when a named threat actor materially matters today: who they are, primary tactics, recent activity or impact.

### 2.9 Per-item research fields
For every selected item, establish: title, date, source, domain, surface, signal type, half-life, AI impact (None / Enabling / Amplifying / Governing / Targeted), summary, extracted statistics, and — when applicable — breach-specific research detail (e.g. records exposed, data types, discovery vs. disclosure, attack vector, regulatory clock — useful for the TXT brief's prose and for `extracted_statistics`). This research-level vocabulary is not a JSON field-naming instruction: when building the JSON, breach information goes into the five-field `breach_specifics` object defined in Section 4.5, whose field names control.

Also assess, per item, the lightweight **IAD-Signal marker**: how strongly the item warrants later institutional analysis through the Institutional Analysis and Development lens, and which IAD dimensions (Actors, Rules-in-Use, Arena, Incentives, Interactions, Outcomes, Levers) appear potentially relevant. This is a relevance-plus-dimensions marker, not a written IAD analysis — see Section 4.4 for exactly how this becomes the JSON-only `iad_signal` field. It is a per-item judgment, independent of whatever day-level "IAD LENS" framing (if any) goes into the TXT brief under Section 3.

When the source material for an item contains analytically important institutional evidence — a named rule, authority, statute, policy, or procedure; stated actor reasoning or rationale; a meaningful actor interaction or temporal sequence; or an explicitly identified recurring institutional pattern — also capture, per dimension, a concise evidence-based interpretation, and, where a relationship between tagged dimensions is actually supported by the evidence, a short mechanism statement. See Section 4.4 for the JSON-only `iad_signal.dimension_notes` and `iad_signal.mechanism` fields this becomes. Do not manufacture this detail where the source doesn't support it — a thin item with only `relevance` and `dimensions` populated (or `relevance: "None"`) remains a correct and complete result.

### 2.10 Daily Narrative (required)
Operational synthesis answering: what changed today; did anything escalate, stabilize, or break precedent; and the aggregate role of AI today, in one sentence. No speculation, no restating background conditions.

### 2.11 Strategic Insights
One emerging trend, one policy or market implication, one blind spot or quiet area.

### 2.12 Industry Research Reference (persistent baseline)
A cumulative list of key industry or vendor research used as structural baselines. Append only when a genuinely new report is released; once added, entries persist across briefs. Do not summarize or analyze here — see Section 3.3 for where this lives (TXT-only).

### 2.13 Source universe (coverage baseline, not an allowlist)
Research should cover the established CyberBrief source universe below as a coverage baseline. This is not an allowlist: the LLM remains free to discover and use additional credible sources relevant to today's signals, beyond this universe.

- **Government:** CISA, FBI, DOJ, EUROPOL, ENISA, NCSC, CERT-EU, JPCERT/CC, ACSC (Australia)
- **Policy & Research:** RAND, Brookings, MITRE, Atlantic Council, Carnegie Endowment (Cyber Policy Initiative), CFR, Lawfare, UK AI Security Institute (AISI), The Alan Turing Institute
- **Journalism & Tech Industry:** KrebsOnSecurity, BleepingComputer, Ars Technica, CyberScoop, Wired, The Record, Bloomberg Tech, Microsoft, Meta, Amazon, Google, Bloomberg, NYT, Hacker News, Dark Reading, TechCrunch Security
- **Vendor & Security Research:** Mandiant/Google Cloud Threat Intelligence, CrowdStrike Blog, Cisco Talos/TalosIntelligence, Palo Alto Unit 42, Wiz, Checkmarx, Sysdig, Recorded Future, Rapid7, SentinelLabs, Cyble, Black Duck, Synopsys, Microsoft Threat Intelligence (MSTIC), ESET Research, Check Point Research
- **Ethical Hacker & Bug Bounty:** HackerOne Hacktivity, Bugcrowd Blog
- **OSINT/Social:** Reddit, X, LinkedIn, Telegram, Dark Web forums, Mastodon/Fediverse security communities, GitHub repositories
- **Primary Breach Disclosures:** SEC EDGAR Form 8-K Item 1.05, HHS OCR Breach Portal, State AG notification sites, UK ICO, OAIC (Australia), CNIL (France)
- **Secondary Breach Tracking:** DataBreaches.net, Have I Been Pwned (HIBP) blog/announcements

### 2.14 Evidence quality
Use evidence appropriate to the claim. Prefer primary and authoritative sources when available. Use credible secondary reporting for discovery and context. Corroborate material claims when the underlying evidence is uncertain, disputed, indirect, or based primarily on secondary reporting. This is a governing principle, not a mechanical two-source requirement.

### 2.15 Collection versus selection
Source discovery and research (Sections 2.13-2.14) produces candidate developments, not final signals. The existing selection criteria in Section 2.7 — including the 6-8-item guidance and the informativeness standard — determine which candidates become final CyberBrief items.

### 2.16 Evidence preservation (source URLs)
For every selected CyberBrief item, preserve the HTTP/HTTPS URL(s) of the evidence actually used to support that observation — not every page encountered during research, only evidence materially used to support the selected observation. These URLs become the item's required `source_urls` array in the canonical JSON record (Section 4.3). `source` remains the separate human-readable source/outlet field; `source_urls` holds one or more supporting evidence URLs.

## 3. Writing the TXT brief (human-readable artifact)

Write the canonical daily TXT brief using the synthesis from Section 2. This is the artifact for human review.

### 3.1 Format
Format is canonical — do not change section structure or ordering without an explicit decision from Charles. The current section order (per recent production briefs) is: daily intelligence summary header; per-item entries (each with Summary and Extracted Statistics, and other Section 2.9 fields as written); Adversary Spotlight (when present); Registry Abuse Watch / LLM Misuse Tracker (when present); Inflection Watch; Longitudinal Arcs; Daily Narrative; end-of-brief marker. On a day with zero qualifying items (Section 2.7), the brief must state that result explicitly rather than omitting explanation or silently shipping a shorter brief.

### 3.2 IAD LENS (TXT-only)
The TXT brief may carry a day-level **"IAD LENS"** line or section — an analytical throughline for the day, in prose. This is a TXT presentation element only.

### 3.3 Industry Research Reference (TXT-only)
The TXT brief may carry an **"INDUSTRY RESEARCH REFERENCE (Cumulative Baseline)"** section per Section 2.12. This is a TXT presentation element only.

### 3.4 Boundary rule
**Neither of the two sections above may cause a corresponding top-level field in the canonical JSON.** `iad_lens` and `industry_research_reference` are not valid top-level JSON keys under Schema v1 (`cyberbrief.schema.json` sets `additionalProperties: false` at the top level, and neither key is declared) — see Section 4.8. Writing the TXT does not drive, and is not driven by, building the JSON.

### 3.5 Output
Write to `CyberBrief/Briefs/YYYYMMDD_cyberbrief.txt` (or `CyberBrief/Briefs/<start>_<end>_cyberbrief_retrospective.txt` for a retrospective covering a missed range), using the current date(s) for the run.

## 4. Building the canonical JSON record (independent, Schema v1)

### 4.1 The JSON is a research record, not a rendering
The canonical JSON is an independently constructed structured record of the day's research, governed by `cyberbrief.schema.json` and described in full in `Canonical_CyberBrief_Schema_v1.md`. Build it from the same analytical brief (Section 2) used for the TXT — do not derive it by parsing, transcribing, or "serializing" the TXT file, and do not treat TXT section headings as a source of JSON key names. This replaces the prior `Feb_20_2026_JSON_Serialization_Prompt.txt` approach, which instructed literal serialization of TXT sections into JSON and is the documented cause of schema drift (see Section 4.8).

### 4.2 Required top-level shape
Per `cyberbrief.schema.json`:

- Required: `date`, `signal_counts` (`structural_shift`, `policy_evolution`, `incident` — integer counts), `items` (array).
- Optional, include when applicable, `null` when not: `micro_tracking`, `inflection_watch`, `longitudinal_arcs`, `daily_narrative`, `adversary_spotlight`, `strategic_insights`.
- `adversary_spotlight`'s and `micro_tracking`'s required internal shapes, when either is present, are fixed and fully required — see Section 4.6 and Section 4.7 respectively.
- No other top-level keys are permitted (`additionalProperties: false`).
- **Zero-item day (Section 2.7):** the candidate JSON remains schema-valid with `"items": []` and `"signal_counts"` set to `{"structural_shift": 0, "policy_evolution": 0, "incident": 0}` — `cyberbrief.schema.json` imposes no minimum on `items` and only `minimum: 0` on each `signal_counts` field, so this requires no schema change.

### 4.3 Required item shape
Each entry in `items` requires: `title`, `date`, `source`, `source_urls` (array of one or more HTTP/HTTPS evidence URLs — see Section 2.16 for what to preserve; `source` stays the human-readable source/outlet field, `source_urls` is separate and required), `domain`, `surface`, `signal_type` (`Incident` | `Policy Evolution` | `Structural Shift`), `half_life` (`Short` | `Medium` | `Long`), `ai_impact` (`None` | `Enabling` | `Amplifying` | `Governing` | `Targeted`), `arc`, `iad_signal`, `summary`, `extracted_statistics` (array, may be empty), `breach_specifics` (object or `null` — required internal shape specified in Section 4.5). No other item keys are permitted.

### 4.4 `iad_signal` (item-level, JSON-only)
For every item, set at minimum:

```json
"iad_signal": {
  "relevance": "None | Low | Medium | High",
  "dimensions": ["Actors", "Rules-in-Use", "Arena", "Incentives", "Interactions", "Outcomes", "Levers"]
}
```

`dimensions` is zero or more of the seven allowed values; when `relevance` is `"None"`, `dimensions` must be `[]`. This is the JSON-only formalization of the Section 2.9 IAD-Signal marker — assess it from the item itself, per the marker definition in `Canonical_CyberBrief_Schema_v1.md` §4.10. Do not derive it from, or make it depend on, the TXT's day-level "IAD LENS" line (Section 3.2) — they are different things at different levels (item vs. day) serving different purposes (structured marker vs. narrative prose).

#### 4.4.1 `dimension_notes` and `mechanism` (item-level, JSON-only, optional)

`iad_signal` may optionally extend to:

```json
"iad_signal": {
  "relevance": "High",
  "dimensions": ["Actors", "Rules-in-Use", "Incentives", "Levers", "Outcomes"],
  "dimension_notes": {
    "Rules-in-Use": "Court-authorized seizure under an unsealed affidavit, Southern District of California."
  },
  "mechanism": {
    "statement": "A court-authorized domain seizure disabled infrastructure the targeted platforms depended on.",
    "relationships": [
      {
        "from": "Rules-in-Use",
        "relationship": "enables",
        "to": "Levers",
        "status": "Observed",
        "evidence": "\"DOJ and FBI announced court-authorized seizures of three domains\""
      }
    ]
  }
}
```

Rules for populating these two fields:

- **`dimension_notes` stays sparse.** Add a note only for a dimension where the source contains analytically important institutional evidence per the Section 2.9 criteria (named rule/authority/statute/policy/procedure; stated actor reasoning; meaningful interaction or temporal sequence; explicitly identified recurring pattern). Do not add a note merely to populate every dimension listed in `dimensions`. Omit the field entirely, or set it to `{}`, when no dimension warrants one.
- **`mechanism` is optional and all-or-nothing.** Create it only when a relationship between tagged dimensions is actually supported by the evidence in the item. Omit it entirely, or set it to `null`, otherwise — including for every item where `relevance` is `"None"` or `dimensions` is `[]`. Never populate `mechanism` to make a thin item look more institutionally rich than the source supports; a correctly thin result (empty `dimension_notes`, `mechanism: null`) is a valid, expected outcome, not a gap to fill.
- **Every relationship in `mechanism.relationships` carries an explicit `status`:** `Observed` (the source states the connection directly), `Analytical Inference` (reasonably drawn from evidence in the record, with that evidence cited), or `Hypothesis` (a plausible research question or candidate explanation not yet established by the evidence, with the prompting observation cited as `evidence`). A Hypothesis is a legitimate research object — the Observatory's research process runs Observation → Pattern → Hypothesis → Model → Writing — and should be preserved with that label, never discarded merely because it isn't yet an established finding, and never written or read as if it were `Observed`.
- **Do not treat the same fact recorded under two schema fields as independent corroborating evidence** for a relationship. An Analytical Inference must trace to evidence beyond the bare co-occurrence of two dimension tags.

These two fields are optional at the schema level specifically so that the four existing Schema v1 canonical files (2026-08-29 through 2026-09-01) remain valid without modification — see Section 4.8's prohibition on retroactively touching historical records.

### 4.5 `breach_specifics` (item-level, object or `null`)

Required on every item; its value is `null` unless the item involves a data breach or related compromise, in which case it is an object containing **exactly these five fields — no others**:

```json
"breach_specifics": {
  "victim": "...",
  "actor": "...",
  "vector": "...",
  "data": "...",
  "status": "..."
}
```

- `victim` — string. The affected organization(s) or population.
- `actor` — string. The attributed actor, when known.
- `vector` — string. The compromise vector.
- `data` — string. The exposed or affected data.
- `status` — string. Current breach/disclosure status.

These five names are the only field names Schema v1 recognizes for `breach_specifics` (`cyberbrief.schema.json`'s `breachSpecifics` definition sets `additionalProperties: false` and requires all five). **The executable schema's field names control.** Section 2.9's research-level breach vocabulary (records exposed, data types, discovery vs. disclosure, attack vector, regulatory clock) describes what to investigate and is useful for the TXT brief's prose — it is not a JSON key-naming instruction. When building the JSON, map that research into exactly the five fields above.

For items without applicable breach-specific information: `"breach_specifics": null`.

### 4.6 `adversary_spotlight` (top-level, object or `null`)

Included only when Section 2.8's condition is met (a named threat actor materially matters today); `null` or omitted otherwise.

When present, `adversary_spotlight` is an object containing **exactly these eight fields — no others — all required**:

```json
"adversary_spotlight": {
  "actor": "...",
  "classification": "...",
  "known_aliases": ["...", "..."],
  "attributed_nation": "...",
  "active_since": "...",
  "todays_relevance": "...",
  "ttps_today": "...",
  "historical_pattern": "..."
}
```

- `actor` — string. Who the actor is.
- `classification` — string (e.g. Nation-State, Cybercriminal, Hacktivist).
- `known_aliases` — **array of strings.** Not a single string — this has already drifted in production practice (see below).
- `attributed_nation` — string.
- `active_since` — string.
- `todays_relevance` — string. Why this actor matters today (Section 2.8's "recent activity or impact").
- `ttps_today` — string. Primary tactics relevant today (Section 2.8's "primary tactics").
- `historical_pattern` — string.

Schema v1 (`cyberbrief.schema.json`'s `adversarySpotlight` definition) sets `additionalProperties: false` and requires all eight fields whenever the object is present. Section 2.8's three-line description ("who they are / primary tactics / recent activity or impact") is the research-level summary of what to establish; it maps onto `actor` / `ttps_today` / `todays_relevance`, but the four additional structural fields above (`classification`, `known_aliases`, `attributed_nation`, `active_since`) must also be populated — they are not optional extras. In particular, `known_aliases` must be a JSON array even when there is only one alias or the aliases read naturally as a short descriptive phrase; do not write it as a single free-text string (a real production file has done this, and it fails validation).

### 4.7 `micro_tracking` (top-level, object or `null`)

When `micro_tracking` is included (per Section 2.6), it must contain **both** of the following string fields — never just one:

```json
"micro_tracking": {
  "registry_abuse": "...",
  "llm_misuse": "..."
}
```

Section 2.6 applies Registry Abuse and LLM Misuse tracking independently ("apply only when events occur"), but Schema v1 (`cyberbrief.schema.json`'s `microTracking` definition) requires both keys whenever the object itself is present — there is no partial `micro_tracking` object. If one area had no meaningful development today, say so explicitly and briefly (e.g. `"registry_abuse": "No registry abuse activity observed today."`) rather than omitting that key. If neither area had any activity, omit `micro_tracking` entirely (set it to `null`) rather than including an object of two "nothing happened" strings.

### 4.8 Explicit prohibitions
- Do **not** generate a top-level `iad_lens` field. (Production JSON has historically carried a stray top-level `iad_lens` string mirroring the TXT's day-level IAD LENS sentence — this violates Schema v1 and is exactly the drift this workflow exists to stop. Confirmed by running the fixed validator against `CyberBrief/Data/20260825_cyberbrief.json`: `Additional properties are not allowed ('iad_lens' was unexpected)`.)
- Do **not** generate a top-level `industry_research_reference` field.
- Do not infer or add a JSON field merely because a similarly named section or heading exists in the TXT brief.
- Do not modify Schema v1 to make the day's output easier to fit. If a real day's research doesn't fit the schema, that's a validation failure to report (Section 5), not a reason to loosen the contract.
- Do **not** populate `iad_signal.dimension_notes` or `iad_signal.mechanism` to manufacture institutional richness a thin item doesn't have. A correctly thin result — `dimension_notes` omitted or `{}`, `mechanism` omitted or `null` — is a valid outcome, not a gap to fill (Section 4.4.1).
- Do **not** write, or later treat, a `Hypothesis`-status relationship as if it were `Observed` or `Analytical Inference`. Do not discard a genuine hypothesis merely because it isn't yet an established finding — label it and preserve it (Section 4.4.1).
- Do **not** retroactively add `dimension_notes` or `mechanism` to the existing canonical files for 2026-08-29 through 2026-09-01, or to any other historical record. These two fields are optional in Schema v1 specifically so historical records remain valid unmodified.

### 4.9 Candidate file — do not overwrite the canonical record until validated
Write the JSON to a **candidate** path first, not directly to the day's canonical filename:

```
CyberBrief/Data/.candidate/YYYYMMDD_cyberbrief.candidate.json
```

(create the `.candidate/` subdirectory if it does not exist). Only after the candidate passes validation (Section 5) is it copied/renamed to the canonical path `CyberBrief/Data/YYYYMMDD_cyberbrief.json`. This guarantees an invalid candidate can never overwrite an already-valid canonical record for that date, and gives a concrete artifact to inspect when validation fails.

## 5. Validation gate

Run, from any working directory:

```
python3 OSS_Observatory/validators/cyberbrief_validator.py CyberBrief/Data/.candidate/YYYYMMDD_cyberbrief.candidate.json
```

(use the actual absolute or relative path to the candidate file for that run; the validator resolves `cyberbrief.schema.json` relative to its own location, not the caller's cwd, so this works regardless of where the run's working directory happens to be).

### 5.1 On success
`CYBERBRIEF PASSED VALIDATION`. Promote the candidate: copy/rename it to `CyberBrief/Data/YYYYMMDD_cyberbrief.json`. Proceed to Section 6.

Update the run record (Section 12.5): mark stage 4 (Schema validation) `PASS`, and mark stage 5 (Canonical JSON promotion) `DONE` with the promoted canonical path. If this validation or promotion is not the first attempt for this date, also log it in Execution Notes (Section 12.4).

### 5.2 On failure
The validator exits non-zero and prints `CYBERBRIEF FAILED VALIDATION`, the exact `Reason:`, and the `Location:` (JSON path) of the offending field. When this happens:

- **Report the exact validation error to Charles** — the reason and location, verbatim from the validator output.
- **Do not treat the run as successful.**
- **Do not update `MORNING_BRIEF.md`.**
- **Do not update the Long Half-Life tracker.**
- **Do not present the invalid candidate as the canonical daily brief.**
- **Do not silently weaken or modify the schema to make the output pass.**
- Leave the invalid file at its candidate path (do not delete it — it's the evidence) and do not touch the existing canonical JSON for that date, if one already exists.
- The TXT brief (Section 3) may still be presented on its own merits — TXT output is not gated by JSON validation — but the run as a whole is not complete until the JSON is valid, and that should be stated plainly rather than left implicit.
- Update the run record (Section 12.5): mark stage 4 (Schema validation) `FAIL`, copying the validator's `Reason:` and `Location:` output into the run record verbatim, and mark stages 5-8 (Canonical JSON promotion, CSV roll-up, MORNING_BRIEF.md update, Long Half-Life tracker update) `SKIPPED (validation failed)`. The run record itself is still written — it is the evidence of the failure, not something withheld because the run failed. If a corrected candidate is subsequently validated for the same date, log the correction and the repeated validation in Execution Notes (Section 12.4).

## 6. CSV signal roll-up

Produce `CyberBrief/Data/YYYYMMDD_signal_rollup.csv`, one row per distinct signal pattern (not per story), grouped by Domain, Surface, and Signal Type — derived from the same validated set of items as the promoted JSON, not re-derived from TXT prose.

Columns, exact order: `Date, Domain, Surface, Signal Type, Distinct Signal Count, Volume, Comments`.

Volume classification: **Low** = 1 distinct story; **Medium** = 2-3; **High** = 4+.

Rules: do not invent or infer signals not present in the day's items; do not include story titles, summaries, or prose in this file — it is structured sensemaking, not narrative.

Produce the CSV only after the JSON has been promoted (Section 5.1) — if validation fails, do not produce a CSV for that run.

## 7. Update persistent trackers/state

Only after a successful validation and promotion (Section 5.1):

- Update `CyberBrief/Briefs/MORNING_BRIEF.md` with the day's brief summary and archive index entry.
- Update `CyberBrief/Data/LongHalfLife/LongHalfLife_Tracker_May2026.xlsx` with any new Structural Shift (Long Half-Life) items from today's run.

If no lock file (e.g. a `.~lock.*#` file alongside the workbook, as created by Excel/LibreOffice) is present, proceed normally. If a lock file is present, do not treat its mere presence as sufficient to skip: compare its modification time to the tracker workbook's own modification time.

- If the workbook's modification time is **later** than the lock file's modification time, treat the lock as stale/orphaned — a successful workbook write demonstrably occurred after the lock was created. Proceed with the tracker write via openpyxl, verify the appended row by re-reading the workbook, and record the stale-lock reasoning (both timestamps) in the Run Record.
- If the workbook is **not** newer than the lock file, timestamps are unavailable, or the comparison is otherwise inconclusive, treat the lock as potentially active: do not force a write; note it in the run's presentation output and let Charles know it needs to be updated once the file is closed.
- Never delete the lock file as part of normal CyberBrief production, regardless of which branch above applies.

Uncertainty defaults to skipping the write — this rule only ever permits a write when there is positive evidence (a later workbook modification time) that the lock has already been safely written through before.

Update the run record (Section 12.3) for each of the two trackers independently: mark stage 7 (MORNING_BRIEF.md update) and stage 8 (Long Half-Life tracker update) each `DONE` or `SKIPPED (<reason>)`. A locked tracker is recorded on its own line, e.g. `SKIPPED (locked: .~lock.LongHalfLife_Tracker_May2026.xlsx#)` — this is the durable record of the skip, in addition to telling Charles in the run's presentation output.

## 8. Present the finished brief

Present the brief to Charles as today's CyberBrief. The conversational screen presentation (Section 8.3) is the primary human-consumption view of the completed run. State plainly which of the three artifacts (TXT, JSON, CSV) were produced and, if the JSON failed validation, that the run is incomplete pending a fix — do not present a partial or invalid run as a normal, successful one.

### 8.1 Two temporal modes

CyberBrief operates in two complementary temporal modes, and the two are not required to co-occur:

- **Manually initiated research continuity** — a CyberBrief run (Sections 1-7, 12) is presently initiated manually (for example, an explicit request such as "Run today's brief"), not by autonomous or scheduled initiation; autonomous/scheduled initiation is deferred and is not the current operating mode. Once initiated, production proceeds independently of whether anyone is present to discuss it, and research must still happen on its correct production day regardless of later conversational participation.
- **Attended research conversation** — a conversation about a brief (Section 8.2) may begin immediately after production or considerably later, including a conversation about an already-completed brief from a prior day.

Conversational participation is never a prerequisite for production once initiated. A day whose production was initiated still produces a complete, valid brief with no conversation about it; a conversation days later is still a legitimate way to engage with it.

### 8.2 Conversation as the primary research interface

The LLM conversation — not the TXT file — is CyberBrief's primary human-consumption interface. Its purpose is to create intellectual affordances that a static file cannot: read, notice, question, investigate, connect, reconsider, develop. This is a research interaction pattern, not a required workflow or a state machine with defined steps — a conversation may use as much or as little of it as the moment calls for.

This does not diminish the TXT, canonical JSON, or CSV roll-up (Sections 3-6): they keep their existing purposes unchanged as the durable, non-conversational record of each run.

### 8.3 Screen presentation format

Render the completed brief to the screen as follows. This is a derived rendering of the completed analysis, not a fourth canonical artifact — it requires no additional research, creates no new canonical research state, does not alter the analysis, classifications, or fields Section 2 already produced, and does not replace the TXT, canonical JSON, CSV roll-up, Run Record, or trackers.

- **Open with signal counts and a concise synthesis** — the day's Structural Shift / Policy Evolution / Incident counts and total, followed by a short synthesis carrying the substance of the Daily Narrative (Section 2.10): what changed today, whether anything escalated, stabilized, or broke precedent, and the aggregate role of AI today. This is a compact rendering of that existing requirement, not a separate analysis — draw it from the completed brief's Daily Narrative rather than composing a new one.
- **Read first (up to 3):** surface up to three developments that most deserve attention first, each with a compact explanation and an explicit "Why it matters" statement. Choosing which items lead is a presentation judgment only — it does not reclassify, promote, or otherwise change an item's signal type, half-life, or any other field from Section 2's analysis.
- **Remaining developments as scan-level entries:** one compact entry per remaining item, each carrying its single most decision-useful fact, statistic, or implication.
- **Every item — Read First or Scan — carries a compact classification tag:** Signal Type, Half-Life, and AI Impact, taken directly from the completed canonical briefing. This is a presentation of existing values only; it performs no reclassification or new analysis.
- **Surface IAD relevance when present:** when an item's completed `iad_signal` (Section 2.9/4.4) has a relevance above `None`, note that relevance — and, when populated, the applicable dimensions — compactly alongside the item. Full dimension notes, mechanism relationships, and epistemic-status detail (Section 4.4.1) are not rendered by default and remain available in the canonical record for conversational follow-up.
- **Compact closing sections**, only when the day's brief has content for them: Inflection Watch, material Longitudinal Arc movement (the arcs that actually moved today, not every defined arc), Adversary Spotlight, Strategic Insights (Section 2.11's one trend / one policy-or-market implication / one blind spot), and Micro-tracking (Section 2.6) when Registry Abuse and/or LLM Misuse tracking contains relevant activity today.
- **Preserve every selected item.** The screen presentation reorders and compresses for readability; it never drops, merges, or silently excludes a selected development.
- **Suppress empty, redundant, or non-informative fields** — null fields should not appear on screen. Negative-result fields (e.g., no registry-abuse activity today) should normally be omitted as well, unless the absence itself is materially informative in the context of the day's analysis.
- **Analytical fidelity is not the same as detail density.** Secondary Adversary Spotlight fields (classification, known_aliases, attributed_nation, active_since, historical_pattern), the full extracted_statistics array, the full breach_specifics structure, detailed IAD dimension notes and mechanisms, the Industry Research Reference, and similar supporting detail remain in the canonical artifact and are retrievable conversationally on request rather than rendered by default.
- **Do not reproduce the full TXT structure** — the screen presentation is a distinct, denser layout for rapid reading, not a re-formatted copy of Section 3's format.
- **A quiet day stays quiet.** Do not expand, embellish, or pad the screen presentation to make a low-item or zero-item day appear more substantial than it was.

This format governs the screen presentation only. It does not change Sections 3-7 or their artifacts, and it introduces no new schema, validator, script, database, or file.

### 8.4 Presentation and production are temporally separable

Presenting or discussing a brief may happen immediately after production or later, against an already-completed canonical CyberBrief. Beginning a later conversation about a prior day's brief must never rerun production, redo research, re-promote artifacts, or duplicate tracker updates — the completed run remains the single source, and the conversation is read-only against it unless Charles explicitly asks for something new.

Phrases like "Run today's brief" or "Discuss Monday's brief" are illustrative only — this is not a formal command language, parser, or prompt catalog. Additional conversational modes (7-day or 30-day lookbacks, a hacking-focused pass, a governance-focused pass, IAD or sub-IAD framing, forward-looking inquiry) are expected to emerge from actual use and are not formalized now.

### 8.5 Provider independence and conversational presentation

Provider independence, as established elsewhere in this workflow and in the LLM Execution Contract, applies to the execution boundary, the canonical research structure, validation requirements, and the durable research artifacts (Section 3). It does not require a universal or provider-neutral conversational UI.

A certified provider presents and discusses its own completed execution in its own native conversational environment — Claude presents Claude's own execution, and a future second or third provider would do the same in theirs. This workflow does not require a common UI, dashboard, blog, presentation service, or application layer built solely to normalize presentation across providers. Presentation differences across providers are not automatically normalized away; they may become useful analytical variance rather than a defect to correct.

This section does not change the Analytical Variance Framework (AVF). AVF tracks analytical variance between independent CyberBrief executions across its own pipeline (Evidence → Selection → Classification → Interpretation → Longitudinal Meaning); researcher interaction is a different object and is not tracked as an additional AVF stage. Interaction is instead preserved through the research-conversation corpus (research/RESEARCH_MILESTONES.md, Architecture.md Section 8), not through AVF.

Finalize the run record (Section 12.7): add the `Run completed` timestamp and confirm stage 9 (Brief presentation) is marked `DONE`, and that the other eight stage lines already reflect the run's actual outcome. Confirm also that Execution Notes (Section 12.4) reflects every material event from the run, not just the final state.

## 12. Run record (audit artifact)

Every CyberBrief run — whether it succeeds, fails, or is only partially completed — produces one run record. Its purpose is narrow: let a run's outcome be reconstructed from disk alone, six months later, without relying on chat or conversation history. It supplements the artifacts and gates already defined in Sections 3-8 and changes nothing about the CyberBrief methodology, Schema v1, the validator, or existing failure semantics.

### 12.1 Location and naming

- Daily run: `CyberBrief/Data/YYYYMMDD_run_record.md`
- Retrospective run: `CyberBrief/Data/<start>_<end>_run_record.md`

Same date-naming convention and same `CyberBrief/Data/` location as the canonical JSON and CSV (Section 9). Each run produces its own dated file; never overwrite or delete a prior date's run record.

### 12.2 Creation

Create the run record first, before Section 2 (Research) begins, with:

- `Run started` — current timestamp, ISO 8601 with timezone offset, in CyberBrief's authoritative timezone `America/Chicago` (Section 2.7) — a named, DST-aware timezone, not a fixed UTC offset.
- `Run type` — `Daily` or `Retrospective (<start>–<end>)`.
- `Provider` — the organization/vendor supplying the LLM executing this run (e.g., `Anthropic`).
- `Model` — the specific model identifier used for this run (e.g., `claude-sonnet-5`), not a family name or marketing label. If the runtime does not expose a specific model identifier, record `unknown` rather than guessing.
- `Execution environment` — how the run was executed (e.g., `Cowork interactive session`, `scheduled task`, `standalone script`), plus a session or run identifier where available.
- `Workflow ref` — `OSS_Observatory/cyberbrief_production_workflow.md`.
- `Workflow commit` — the current Git commit hash of the OSS_Observatory repository, captured via `git -C OSS_Observatory rev-parse HEAD` (or the equivalent invocation from the run's working directory). If the repository or command is unavailable, record `unknown` rather than blocking the run.
- The nine-stage checklist below (Section 12.3), all stages initially marked `PENDING`.
- An empty `## Execution Notes` section (Section 12.4), initially `(none)`.

### 12.3 Stage checklist and updates

The run record tracks nine stages, each updated in place as it is reached:

1. Research / analytical brief (Section 2)
2. TXT generation (Section 3)
3. Candidate JSON generation (Section 4)
4. Schema validation (Section 5)
5. Canonical JSON promotion (Section 5.1)
6. CSV roll-up (Section 6)
7. MORNING_BRIEF.md update (Section 7)
8. Long Half-Life tracker update (Section 7)
9. Brief presentation (Section 8)

Each stage is updated to exactly one of `DONE`, `SKIPPED (<reason>)`, or — stage 4 only — `PASS`/`FAIL` (Section 12.5). Where a stage produces a canonical artifact, record its path on the same line, e.g.:

```
2. TXT generation                    DONE  -> CyberBrief/Briefs/YYYYMMDD_cyberbrief.txt
```

Each stage field holds only that stage's final status. It is not a history: if a stage was attempted, corrected, or repeated more than once before reaching that final status, the checklist line alone does not preserve that — log it in Execution Notes (Section 12.4) instead.

### 12.4 Execution Notes (material execution events)

The nine-stage checklist (Section 12.3) is deliberately single-valued — each stage holds one final status. It is not designed to hold a history of retries, corrections, or repeated attempts, and should not be stretched to do so.

When execution includes a material event that the final stage status alone would not accurately convey, append a concise, chronological entry to the run record's `## Execution Notes` section (Section 12.9 template). Material events include, without limitation:

- correcting an artifact after it has already been validated or promoted;
- validating a candidate more than once for the same date;
- promoting a canonical artifact more than once for the same date;
- regenerating a downstream artifact (for example the CSV, `MORNING_BRIEF.md`, or a tracker entry) because an upstream artifact it depends on changed after the downstream artifact was first produced;
- recovering from, or retrying after, a failure;
- any other execution event needed to reconstruct, from the run record alone, how the run reached its final canonical state.

Each entry must describe what actually occurred, including any intermediate state that was later superseded — not restate only the final successful outcome. Entries are appended in the order the events happened and are never edited or deleted once written, so the section reads as a chronological account rather than a summary. Do not log ordinary, single-pass stage completions here — Execution Notes exists only for what the Section 12.3 checklist cannot represent.

Execution Notes is a plain, append-only list of short entries within the same run-record file — not a separate log file, a database, or an artifact-versioning mechanism. An entry describes what happened to a superseded artifact (what it contained, why it was superseded, and by what); it does not require retaining the superseded artifact itself, which is why this requires no new file-preservation, versioning, or logging infrastructure.

### 12.5 Recording validation

Stage 4 (Schema validation) is recorded as `PASS` or `FAIL`, per Section 5.

On `PASS`: stage 5 (Canonical JSON promotion) is marked `DONE` with the promoted canonical path, per Section 5.1, and the run proceeds normally through stages 6-9.

On `FAIL`: copy the validator's `Reason:` and `Location:` output into the run record verbatim beneath stage 4, then mark stages 5-8 (Canonical JSON promotion, CSV roll-up, MORNING_BRIEF.md update, Long Half-Life tracker update) `SKIPPED (validation failed)`, matching the existing prohibitions in Section 5.2. Stage 9 (Brief presentation) is still marked `DONE` once Section 8 reports the failed run to Charles — the run record does not change what gets presented, only confirms that the presentation happened.

### 12.6 Recording nonfatal exceptions

A stage skipped for a reason other than validation failure (for example, Section 7's locked-tracker case) is recorded on its own line with a one-line cause, not a separate log:

```
8. Long Half-Life tracker update     SKIPPED (locked: .~lock.LongHalfLife_Tracker_May2026.xlsx#)
```

### 12.7 Completion

At Section 8 (Present), add `Run completed` with a timestamp and confirm the final status of all nine stages reflects the run's actual outcome. Execution Notes is not summarized or cleared at completion — every entry logged during the run remains in the file exactly as written.

### 12.8 Preservation

The run record is written and updated regardless of validation outcome. Unlike the canonical JSON and CSV (Sections 4.9 and 6), it is not gated behind validation success — its purpose is specifically to preserve evidence of failed or partial runs. Do not fold it into, or derive it from, the canonical JSON, the TXT brief, or MORNING_BRIEF.md; it is a separate, minimal artifact. This applies equally to Execution Notes: entries are preserved as written, regardless of the run's final outcome.

### 12.10 Scope

The run record is a single flat Markdown file per run — not a database, not a logging framework, not a telemetry system, and not a general audit subsystem. It does not track anything beyond the nine stages above and the Execution Notes entries described in Section 12.4. Execution Notes does not introduce artifact versioning, a separate validator log, or Git tracking of CyberBrief production data — it is a short list of plain-text entries in the same file, describing events in words rather than preserving the superseded artifacts themselves. If future needs exceed what this file can hold, that is a deliberate design change to make explicitly, not a reason to let this section drift.
